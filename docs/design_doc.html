Detecting Machine-Generated Code and Attributing Its Source LLM

An end-to-end, reproducible ML system built for SemEval-2026 Task 13: decide whether a code snippet was written by a human or an LLM, and if by an LLM, which model family wrote it. Designed to run end-to-end on a free Kaggle GPU.

1Business problem

LLMs now write a large share of code. Organizations need to know when, and with which model, because that affects trust, compliance and cost.

Education & hiring

Programming courses and coding interviews need a signal that a submission was LLM-written. A false accusation is expensive, so the system must expose calibrated probabilities and a tunable threshold, not a hard verdict.

Software supply chain

Teams want to flag AI-generated code in repositories for review policy, licensing exposure and security audits (provenance of what entered the codebase).

Forensics & model attribution

Knowing the likely generator family (Qwen, DeepSeek, Llama, GPT, …) helps trace the origin of bulk-generated or malicious code and monitor which models are used.

What makes it hard

  • Distribution shift. Detectors that reach ≈0.99 macro-F1 on seen languages drop sharply on unseen languages and domains (baseline fell from 0.97 to 0.57 in the original run), a sign of shortcut learning.
  • Severe class imbalance in attribution. About 88% of Task B training rows are human code; each LLM family has only 2K–10K rows, so accuracy is misleading and macro-F1 is the right metric.
  • New generators appear constantly. The unseen-generator test measures whether the model learned model-family traits rather than memorising specific checkpoints.

Problem statement

Task A. Given a code snippet, predict human or machine.
Task B. Given a code snippet, predict one of 11 classes: human plus 10 LLM families (DeepSeek-AI, Qwen, 01-ai, BigCode, Gemma, Phi, Meta-LLaMA, IBM-Granite, Mistral, OpenAI).
Metric. Macro-F1 on seen and unseen slices (language, domain, generator).

2Goals and non-goals

Goals

  • One command / one notebook reproduces every reported number.
  • Honest evaluation: identical test rows per model, confidence intervals, a capacity-matched control.
  • Show robustness behaviour: out-of-distribution splits, shortcut and calibration analysis.
  • Cheap enough for free Kaggle (smoke ≈ 5 min, lite ≈ 35–50 min).
  • Serve a small demo with calibrated probability and explanation signals.

Non-goals

  • Leaderboard-topping scores or training on the full 500K–900K rows.
  • Task C (hybrid / adversarial, 4-way). Out of scope for this release.
  • Using any external training data or third-party pretrained AI-code detectors (disallowed by the task rules).
  • A production service with auth, scaling or monitoring.

5End-to-end flow

What happens when the Kaggle notebook is run top to bottom.

  1. Bootstrap environmentAttach the dataset, enable GPU and Internet, install only missing packages (peft, lightgbm, gradio), clone the repo and pip install -e .. Torch and transformers are never reinstalled.
  2. Discover dataGlob parquet files, print columns, label maps, language and generator counts. Paths are written into the config rather than hard-coded.
  3. Build splitsStratified subsample by label × language (Task B caps human share), exact and MinHash near-duplicate removal against every eval split, then create ID-val and OOD splits (held-out language Java; held-out generators). Writes data_report.json.
  4. Extract features (cached)Vectorised stylometric features, z-scored on train statistics; token-level NLL and predictive entropy from frozen Qwen2.5-Coder-0.5B. Cached to disk once.
  5. Run classical baselines (CPU)Length / whitespace-only shortcut baseline, TF-IDF + LR, stylometry + LightGBM, LM-feature + LightGBM.
  6. Train neural models (GPU, fp16)CodeBERT full fine-tune, CodeBERT + LoRA, GPAD, and the capacity-matched control (same extra layer, entropy bias off). Task B uses class-weighted loss. Best checkpoint kept; results JSON written after every model.
  7. Stack and calibrateLightGBM on transformer logits + features (late fusion). Fit temperature on ID-val; choose the Task A operating threshold from a stated false-accusation cost ratio.
  8. EvaluateAll models on identical rows: macro-F1 with 95% bootstrap CI, McNemar tests, per-language and per-class tables, confusion matrix, ECE before / after shift, normalisation stress test (strip comments, normalise whitespace).
  9. BenchmarkLatency p50/p95 and throughput at batch 1 and 32; fp32 vs fp16 on GPU; fp32 vs int8 dynamic quantisation on CPU; parameter counts and peak memory.
  10. Report and servemake_report.py turns JSON into summary.md and figures. The Gradio demo loads a checkpoint from the Hub or a local path.

6Layered architecture

Each layer depends only on the layer beneath it, so models, features or evaluation can be changed without touching the rest.

LayerFunctionalityContract with adjacent layer
L1 Data & featuresLoad, subsample, deduplicate, split, truncate, extract features.Provides leak-free DataFrames and cached feature arrays to L2/L3.
L2 ModelingDefines every predictor behind one interface: fit, predict_proba.L3 trains it; L4 only sees probability vectors.
L3 Training & orchestrationConfig-driven training, losses, seeds, early stopping, experiment matrix runner.Emits a probability file and a metadata JSON per model × split.
L4 EvaluationMetrics, CIs, significance, calibration, stress tests, benchmarks.Reads probability files; writes results/*.json.
L5 PresentationNotebook, report generator, demo, docs.Reads JSON and checkpoints only; no business logic.

7Component details

What is inside each component, with the main design decision for it.

L1Data loader & split builder data.py

  • Reads parquet, stratified subsample by label × language; Task B caps human share so all 10 families are visible while eval keeps the true prior.
  • Exact-hash and MinHash near-duplicate removal between train and every eval split.
  • OOD splits: Task A trains on C++/Python and tests on Java; Task B holds out whole generators.
  • Head+tail truncation (192 + 64 tokens) keeps imports and the ending, where style signals live.

Decision: build OOD splits ourselves so they are labeled and identical across models.

L1Feature extractors features.py

  • Stylometry: chars per line, token ratio, whitespace and tab ratios, control-flow density, comment density, identifier length, long-line share, uppercase ratio, and similar. Vectorised, z-scored on train stats, cached.
  • LM features: frozen Qwen2.5-Coder-0.5B gives per-token NLL and predictive entropy; aggregated to mean, std, max, quantiles, top-1 hit rate.

Decision: compute once and cache; never inside forward().

L2Classical models classical.py

  • Length / whitespace-only logistic regression (shortcut baseline).
  • Char 3–5-gram TF-IDF + logistic regression.
  • Stylometry and LM features + LightGBM; permutation importance for interpretability.

Decision: strong cheap baselines first; they also act as a sanity bound on what the transformer must beat.

L2CodeBERT & LoRA lora.py

  • Full fine-tune of codebert-base with a small MLP head.
  • LoRA variant: rank 8 on attention q/v and the head; trains about 1% of parameters.

Decision: report F1, trainable params and wall time side by side.

L2GPAD & control gpad.py

  • One extra transformer block on top of CodeBERT with an additive, content-driven bias on attention scores, then gated stylometric fusion and an MLP head.
  • Config flags: use_entropy, alpha, sign, use_stylometric, num_gpad_layers.
  • Control: same block with alpha=0 and no style, to isolate whether the bias or extra capacity drives gains.

Decision: every claim about the entropy idea must beat its control.

L3Training engine train.py, losses.py

  • One trainer for Tasks A and B, YAML-driven; AdamW with warmup, weight decay, early stopping, fp16 autocast, optional gradient checkpointing and accumulation.
  • Losses: cross-entropy, class-weighted CE, focal (γ=2), logit adjustment for Task B.
  • Seeds set for Python, NumPy, torch and CUDA; probabilities saved per split.

L4Evaluator eval.py, calibrate.py, bench.py

  • Macro-F1/P/R, balanced accuracy, per-language and per-class tables, confusion matrix.
  • 1,000-resample bootstrap CI; McNemar test on identical rows.
  • ECE, reliability diagram, temperature scaling fitted on ID and tested on OOD; PR curve and threshold chosen by cost ratio.
  • Normalisation stress test: strip comments, normalise whitespace and identifiers.
  • Latency p50/p95, throughput, int8 dynamic quantisation, peak memory.

L5Report & demo make_report.py, app/demo.py

  • Turns JSON into summary.md tables and figures; verdict language follows the confidence intervals.
  • Gradio app: paste code → calibrated probability, LM gauges, top stylometric contributors, out-of-range warning.

QATests & reproducibility tests/

  • pytest on CPU in under a minute: tensor shapes, attention masking, determinism, metric correctness, zero train/eval overlap.
  • Smoke preset runs the full pipeline on a tiny fixture before any long run.

8Model design: GPAD

The research idea of the project: bias attention with an uncertainty signal and fuse handcrafted style features, then verify the gain against a control.

Known issue being fixed. In the original code the "entropy" is the entropy of a learned softmax over key self-similarity, not true token-level predictive entropy, and it boosts low-entropy tokens while the README claimed the opposite. The redesign names it attn_entropy_bias, tests both signs, adds true predictive-entropy features from a frozen code LM, and requires a capacity-matched control.

11Runtime design for Kaggle

StepDeviceTarget time (verify on first run)
Data prep, subsample, dedup, splitsCPU≈ 3 min
Classical baselines, Tasks A and BCPU≈ 5 min
LM features (≈25k snippets, len 256)GPU≈ 6–8 min
CodeBERT full fine-tune, Task A (20k, 2 epochs)GPU fp16≈ 8–10 min
GPAD + capacity control, Task AGPU fp16≈ 10–15 min
Task B (balanced subsample, 2–3 models)GPU fp16≈ 10 min
Evaluation, calibration, benchmark, reportGPU / CPU≈ 3 min

Presets. smoke (2k train, 1 epoch, ≈5 min) validates the pipeline; lite (≈20k train, 2 epochs) is the reported run; full is documented only. If over budget, shrink training size before dropping confidence intervals or the control.

Safeguards. Results JSON is written after every model; only the best checkpoint is stored; no tokens in code (Kaggle Secrets); torch and transformers are never reinstalled; report_to="none".

12Risks, limitations and open items

Risks

  • GPAD may not beat its control. Then the honest finding is that LM-entropy features and class-aware training help, not the bias.
  • Shortcut learning on language or formatting may persist; the stress test will quantify it.
  • Reduced data (20k rows) lowers absolute scores versus the competition run; comparisons within the run remain valid.
  • Kaggle limits: session time and quota; mitigated by smoke preset and per-model result files.

Limitations

  • Detector output is evidence, not proof; false accusations carry real cost.
  • Generators released after the dataset are unseen; attribution to a family is probabilistic.
  • Only snippets up to ≈256 tokens are scored (head + tail).
  • Task C (hybrid and adversarial code) is not covered.

Open items to resolve by inspection

  • Exact Kaggle folder names and whether labeled official unseen-language / domain / author test files exist locally. Proxy OOD splits are the fallback.
  • Which metadata columns exist (language, generator, domain) and the final label maps.
  • Measured timings for the lite preset versus the table in section 11.

13Autonomous execution design

The pipeline is built so Claude Code can run it end to end with one launch and no questions. The chat sandbox cannot reach Kaggle, so the controller runs on the owner's machine and drives Kaggle through its CLI.

Phases and gates

  • P0 build locally; CPU tests and fixture run must pass.
  • P1 Kaggle smoke; required stages ok, models beat majority baseline.
  • P2 Kaggle lite; full results table with CIs.
  • P3–P4 report, model card, slide text, commit and tag.

Self-healing

  • OOM: halve batch, checkpointing, shorter sequences.
  • Over time budget: halve training rows, retry once.
  • NaN loss: lower LR, then fp32.
  • Optional stages skip instead of failing; gaps go to KNOWN_GAPS.md.

Decision rules instead of questions

  • README branch chosen by a paired-bootstrap test of GPAD against its control.
  • Missing official OOD labels: proxy splits are used automatically.
  • Numbers in the README are generated from the results JSON.

What still needs the owner

  • One-time Kaggle phone verification, terms acceptance and API token.
  • Exhausted GPU quota or account restrictions.
  • GitHub authentication for the final push; a final read-through.
